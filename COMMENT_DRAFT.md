I looked at this closely and want to lay out the two options concretely before picking one, since they produce different scaling behavior under partial scrape failure, not just different code.

**Where the bug actually lives:** `internal/collector/replica_metrics.go` defaults `kvUsage`/`queueLen` to 0 when a pod's KV cache or queue metric wasn't scraped this cycle (the file has since been renamed from `capacity_metrics.go`, same logic). That 0 flows straight into `internal/saturationv1/analyzer.go`'s `analyzeVariant`, which compares it against `KvCacheThreshold`/`QueueLengthThreshold` with no way to tell "really measured 0" from "never measured." Note the V2 token-based analyzer (`saturation_v2`) has the same exposure in its fallback path (`computeReplicaCapacityFallback`), though it's a narrower, already-flagged corner case there.

**Scenario:** one replica out of two is genuinely at 90% KV usage and would normally be flagged saturated. This cycle, its KV scrape fails. The other replica is healthy at 30%.

**Option A — exclude the pod from the capacity calc entirely.**
The unscraped replica is dropped from both the saturated/non-saturated classification and the spare-capacity averaging for this cycle. Only the healthy replica (30%, well below threshold) drives `AvgSpareKvCapacity`. Concretely: if this is the *only* replica, dropping it leaves zero replicas to average over, and — unless the analyzer has an explicit "no data → don't scale down" gate — an empty average often resolves to a default that reads as roomy, which is exactly the unsafe-scale-down failure mode we're trying to close. It also needs new bookkeeping: you can't just skip it silently, you have to track "excluded" replicas separately from "non-saturated" ones so a summary of skips is still visible.

**Option B — default conservatively (treat as saturated).**
The unscraped replica is treated as if it hit the saturation threshold: it's added to `SaturatedReplicas`, contributes nothing to the spare-capacity average, and is excluded from `AvgKvCacheUsage`/`MaxKvCacheUsage` so the placeholder value doesn't drag those down either. With only the healthy replica now counted as non-saturated, `NonSaturatedCount` drops to 1, which trips the existing `MinNonSaturatedReplicasForScaleDown` (= 2) gate — so `ScaleDownSafe` becomes false automatically, no new gate needed. If it's the *only* replica, it's marked saturated and `ScaleDownSafe` is false and `ShouldScaleUp` likely fires — both correct given we don't know its real state.

**Recommendation: B.** It fails toward the same side as the risk in the bug report — an unscraped-but-actually-saturated pod misread as empty is the dangerous case, and "assume saturated" biases every downstream decision the same direction that failure mode requires (block scale-down, allow scale-up), never the reverse. It also reuses the existing `MinNonSaturatedReplicasForScaleDown` machinery instead of inventing a parallel "excluded" bookkeeping path, so the diff is smaller and there's no new all-excluded edge case to reason about separately from the existing "not enough non-saturated replicas" case, which the code already handles safely.

I implemented B: the collector now tags each `ReplicaMetrics` with `KvCacheUsageMissing`/`QueueLengthMissing` (the 0 is still stored for backward compatibility, but the flag says whether it's real), and `analyzeVariant` treats either flag as an automatic saturation hit, while dropping the placeholder from the usage average/max so it doesn't misreport actual utilization. PR forthcoming with regression tests that fail against the pre-fix behavior (a pod with a missing KV metric reading as `KvCacheUsage=0` gets classified non-saturated and can even flip a 2-replica scale-down from unsafe to "safe").

One thing I didn't fix, flagging so it isn't lost: `saturation_v2`'s `computeReplicaCapacityFallback` also reads `rm.KvCacheUsage` directly for its coarse demand estimate and has a comment acknowledging it's an approximation already. I scoped this fix to the V1 analyzer named in the report; the V2 fallback path could use the same `KvCacheUsageMissing` signal but I didn't want to touch a path that has its own separately-tracked caveat without more discussion.
